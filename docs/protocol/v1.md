# Reflex protocol v1

Wire format for Reflex CLI hosts. Every rule below is part of version 1. Kit 1.0.1.

## Framing

A host reads requests from stdin as bytes with one JSON object per line. It writes exactly one JSON object per line to stdout for each request line. Logs and startup errors go to stderr. State lives for the process lifetime and EOF ends the session. The host’s first argument selects a fixture. Unknown fixtures exit 64.

| Rule | Detail |
| --- | --- |
| Line end | LF (0x0A) ends a line. It is the only line terminator. |
| CR | CR (0x0D) is not a terminator. RFC 8259 reads it as whitespace between tokens. A CRLF line therefore parses. A lone CR between two objects leaves both objects on one line and that line is `json.malformed` with one reply. |
| One reply | Every line gets one reply. A blank line or a line of spaces is `json.malformed`. |
| EOF | Bytes after the last LF form one more line at EOF when there is at least one byte. Nothing after the last LF means no further reply. |
| UTF-8 | A line must be strict UTF-8 (RFC 3629). Overlong forms, encoded surrogates (U+D800 to U+DFFF), values above U+10FFFF, truncated sequences and stray continuation bytes are `json.malformed` at `$`. The reply never echoes the rejected bytes and the session continues with the next line. |
| BOM | A byte order mark is not whitespace. A line that starts with one is `json.malformed`. |
| Controls | A raw NUL or other control character outside a string is `json.malformed`. Inside a string it must be escaped. `\u0000` is a valid escape. |

## Handshake

The first request must be:

```json
{"op":"hello","protocol":1}
```

The reply names the version, the sample and the kit version, then the usual node:

```json
{"kit":"1.0.1","node":{...},"ok":true,"protocol":1,"sample":"outbox"}
```

| Request problem | Reply |
| --- | --- |
| `protocol` missing | `field.missing` at `$.protocol` |
| `protocol` not an Int64 integer | `field.type`, `int.syntax` or `int.range` at `$.protocol` |
| unsupported version | `protocol.unsupported` at `$.protocol` with `"supported":[1]` |
| any other op before a successful `hello` | `protocol.handshake_required` at `$.op` |

A failed `hello` leaves the session un-negotiated and the client may send `hello` again. A repeated `hello` with a supported version is accepted.

## Operations

| op | request keys | effect |
| --- | --- | --- |
| `hello` | `op` `protocol` | Negotiates the version. |
| `ls` | `op` | Returns the focused node. |
| `do` | `op` `action` and optional `input` | Runs one available action of the focused node. |
| host op | `op` and optional `input` | Declared by the sample. The outbox adds `advance` (`ms`) and `network` (`script`). |

`input` must be absent or a JSON object. Absent input is decoded as `{}`. Parameterless actions accept `{}` only.

## Responses

Every response has `ok` and `node`. Rejections add `error`. Samples may add fields to every response: inventory adds `networkAttempts` and the outbox adds `server`.

```json
{"error":{"code":"int.syntax","path":"$.input.quantity"},"networkAttempts":0,"node":{...},"ok":false}
```

A node has `name`, `state`, sorted `actions` and `inputs`. `inputs` maps each parameterised action to a JSON Schema subset: `type` `object` with `properties`, sorted `required` and `additionalProperties` false. Integer fields are `{"type":"integer","format":"int64"}` with optional `minimum` and `maximum`.

A rejected request never reaches a ViewModel, so `node` is unchanged. Business validation is not a wire error: it returns `ok:true` with the error in state.

## Strict decoding

- The request line is RFC 8259 JSON in strict UTF-8. Leading zeros, control characters in strings, lone or reversed surrogate escapes (`\ud800`, `\udc00`, `\ude00\ud83d`) and trailing text are `json.malformed`. A surrogate pair escape such as `\ud83d\ude00` is one character. Nesting deeper than 64 is `json.depth`.
- Keys, `op` names, action titles and schema field names compare by exact UTF-16 code units. There is no Unicode normalisation. `"\u00e9"` and `"e\u0301"` are two different keys and so are `"K"` and `"\u212a"` (KELVIN SIGN). A raw character and its `\u` escape are the same key. String values are kept exactly as sent.
- A key repeated in any object at any depth is `json.duplicate_key` at that key’s path, even inside a field that would be unknown.
- The root must be an object (`request.not_object`).
- Integers are Int64. A literal with a fraction or exponent is `int.syntax` even when its value is whole (`90.0` and `1e2`). An integer literal outside Int64 is `int.range`. A declared `minimum` or `maximum` also yields `int.range`.
- Strings, booleans, objects and arrays match only their own JSON kind. `"90"` is not an integer and `1` is not a boolean (`field.type`).
- `null` is never a value. An optional field is absent instead (`field.type` when present as `null`).
- Keys that a schema does not declare are `field.unknown`.

## Error precedence

The first failure wins, checked in this order:

1. JSON syntax, depth and duplicate keys, in document order.
2. Root is an object.
3. `op` present, a string and known.
4. Handshake done, unless `op` is `hello`.
5. Envelope keys, sorted by UTF-16 code unit: the first unknown key.
6. `action` present, a string and available on the focused node.
7. `input` absent or an object.
8. Schema: unknown keys first (sorted), then each declared field sorted by name (missing, kind, integer syntax, range), depth first into objects and arrays.
9. Host checks thrown by an action or op, such as `field.value` for an unknown outbox outcome.

## Error codes

| code | meaning |
| --- | --- |
| `json.malformed` | Not one valid JSON value or not strict UTF-8. Path is always `$`. |
| `json.depth` | Nesting deeper than 64. Path is `$`. |
| `json.duplicate_key` | A key repeats in one object. |
| `request.not_object` | The root is not an object. |
| `request.unknown_op` | `op` is not `hello`, `ls`, `do` or a host op. |
| `protocol.handshake_required` | No successful `hello` yet. |
| `protocol.unsupported` | The requested version is not supported. |
| `action.unknown` | The focused node does not offer this action. Names are case sensitive. |
| `input.not_object` | `input` is present and not an object. |
| `field.missing` | A required field is absent. |
| `field.unknown` | A key is not declared. |
| `field.type` | A value has the wrong JSON kind or is `null`. |
| `field.value` | A well-typed value outside the host’s accepted set. |
| `int.syntax` | An integer field holds a fraction or exponent literal. |
| `int.range` | An integer is outside Int64 or the declared bounds. |

## Paths

Paths start at `$` (the request object) and use `.key` and `[index]`: `$.op`, `$.input.quantity`, `$.input.rows[0].n`. Keys are written raw with the code units the client sent. An object with `"\u00e9"` and `"e\u0301"` reports `$.e\u0301` because 0x65 sorts before 0xE9.

## Canonical output

Both kits write keys sorted by UTF-16 code unit, no whitespace, integers in decimal and strings with only `"` `\` and control characters escaped (`\n` `\r` `\t` `\b` `\f` and lowercase `\u00XX`). Swift and Kotlin hosts emit byte-identical responses for the same request bytes and state. The runner and the conformance table fail on any byte difference. Other clients may compare parsed values.

## Compatibility

The protocol version is one integer. Adding an operation, error code or response field keeps version 1. Removing one or changing its meaning needs version 2. The kit version is semantic and independent of the protocol.

The line, UTF-8 and key comparison rules above were added on 6 Nov 2026 with kit 1.0.1. They clarify behaviour the first text left open, where Swift and Kotlin disagreed. They add no error code and change no rule a client could rely on on both platforms, so the protocol stays version 1. Conformance cases for every rule above are in `kit/conformance/strict-decoder.json` and both kits run them in their unit tests.
